## Dedicated boot automount profile

`just test-boot-automount IMAGE` runs the regression test for
[bootc#2402](https://github.com/bootc-dev/bootc/issues/2402) (an update
staged after the `/boot` automount idled out is lost at finalization) through
`cargo xtask run-tmt` and bcvk, with the separate opt-in plan
`tmt/plans/boot-automount.fmf`. It does not build `IMAGE`: provide an
ostree-backed Fedora 44 image with the usual tmt dependencies (including
nushell) and the ostree revision under test. bcvk installs it with a GPT ESP
and `/boot` on the root filesystem, the layout where systemd-gpt-auto-generator
puts `boot.automount` over ostree's `/boot` bind mount.

The plan is disabled in ordinary integration runs. The Justfile recipe enables
it with the `boot_automount_lane=required` context and passes `--require-plan`,
so an absent or disabled plan is an error rather than an empty successful run.
The prepare step rejects any guest that is not that layout instead of adapting
it, and the finish step requires the booted `v2` marker, so the test's own skip
on an unsupported layout cannot pass here. Finish also prints the previous
boot's updater, finalize and mount journals before asserting, including when
the test failed earlier.

The test and its helpers are discovered from the pinned revision of upstream
[bootc PR 2634](https://github.com/bootc-dev/bootc/pull/2634), tracked by
[#105](https://github.com/cgwalters-forge/bootc/issues/105), which also owns any
correction to the test source; update the `ref` in the plan when that branch
moves. Both the runner's tmt logs and bcvk's journal and console captures go
under `/var/tmp/tmt`. Keep the recipe's own output too: it records the image
inspection and the checkout being run. Record the bootc and ostree build
commits separately; an image ID or RPM version alone does not identify either.

Acceptance for the ostree fix ([ostree PR
3690](https://github.com/ostreedev/ostree/pull/3690)) needs three fresh VMs on
the same test revision: an affected ostree must fail at the final update
assertion, not in prepare; the fixed ostree must boot `v2`; and an affected
guest whose automount never idles out must boot `v2` as a control. The test
always waits for the idle-out, so the control needs a test variant from #105.
Building images for those ostree revisions, and a CI job for this profile, are
not part of this profile yet.
