## BIOS boot bind regression

The opt-in `boot-bind-fstab` test needs an x86_64 OSTree image with GRUB,
OSTree >= 2026.5 and systemd >= 256. Build `localhost/bootc` from the checkout
first, then run:

```sh
podman build -t localhost/bootc-boot-bind-fstab tmt/fixtures/boot-bind-fstab
cargo xtask run-tmt --context boot_bind_fstab=true localhost/bootc-boot-bind-fstab boot-bind-fstab
```

The fixture enables `[install] boot-bind-fstab = true`; other images retain the
default behavior. The plan selects BIOS firmware through bcvk's fresh `to-disk`
install path, leaving the hybrid layout's ESP unused. The guest records OSTree
and systemd versions and partition types, requires no autofs `/boot`, checks
status after a 180-second idle window, both directly and from a new mount
namespace (where an expired automount fails with EPERM), then stages a
derived image and verifies its digest after reboot. The test has a ten-minute
limit; it does not mask automounts or shorten their timers.

For a negative control, build the same fixture from a pre-fix bootc checkout
with `--build-arg ENABLE_BOOT_BIND_FSTAB=false`, keeping OSTree and systemd
versions fixed, and run the new test harness against that image. This omits
the new config key, which old installers reject, but preserves the direct
layout. The no-autofs assertion is expected to fail on the affected
BIOS layout even if status already tolerates automounts. A passing static check
is not evidence that this VM control or the fixed VM case passed.
