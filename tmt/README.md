## Failed-plan diagnostics

`cargo xtask run-tmt` collects a best-effort `failure-diagnostics.json` before
removing a VM whose TMT plan failed. It does no collection on successful plans.
The bundle lives alongside the existing bcvk captures in
`/var/tmp/tmt/<vm-name>/` (or the existing `--log-dir` / `TMT_LOG_DIR` override),
so the existing CI upload of `/var/tmp/tmt` includes it. With a custom directory,
retain that directory yourself.

**Start with `console.txt` and the `journal*.json*` files, including rotated
journals.** These are retained in place, not replaced by another console/journal
stream. The manifest inventories their names and sizes and explicitly reports
missing/empty captures or an old bcvk without `--log-dir` support.

The manifest identifies the plan, VM, failed tests and observed reboot count or
step from TMT results and referenced logs. Missing evidence is `unknown`; a
reboot timeout alone does not classify the guest failure. VM state is selected
from an allowlist of state and numeric resource/SSH-port fields, never raw
`bcvk inspect` JSON (which contains the private SSH key).

An SSH reachability probe precedes a single `journalctl -b -1` attempt. Each
collector command has a 10-second timeout plus a 1-second forced-kill grace;
output and input files are limited to 256 KiB, with at most 64 results and 64
referenced logs per result, and 128 capture directory entries. The previous-boot
fetch additionally limits output to 1000 lines. Missing tools, unreachable SSH,
absent previous journals and collector failures are recorded without changing
the original failing result. Collection does not retry reboots or extend waits.
Cleanup and `--preserve-vm` keep their existing behavior.
