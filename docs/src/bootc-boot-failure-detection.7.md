# Upgrade/rollback failure detection in bootc

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

This document describes how to detect when a reboot failed to enable the staged image in bootc.

## Overview

bootc uses different mechanisms to detect boot failures depending on the backend (OSTree vs. composefs+UKI) and the specific point of failure. Understanding these mechanisms is crucial for system administrators and automated tooling that needs to detect failed updates.

## OSTree Backend Boot Failure Detection

For systems using the traditional OSTree backend, bootc relies on OSTree's built-in boot failure detection mechanisms.

### Key Services

1. **`ostree-finalize-staged.service`** - Runs during shutdown to finalize staged deployments
2. **`ostree-boot-complete.service`** - Runs early in boot to detect finalization failures

When `ostree-finalize-staged.service` fails during shutdown/reboot, this will create
a stamp file in `/boot`, and then on a subsequent reboot the `ostree-boot-complete.service`
service will detect it, and then itself exit with a failure mode.

You can monitor the success of both services, though for `ostree-finalize-staged.service`
note that the failure occurred during the previous boot's shutdown.


## Composefs Backend Boot Failure Detection

### Key Services

`bootc-finalize-staged.service` finalizes staged composefs deployments during
shutdown. On systems with systemd-boot or GRUB, if finalization returns an error,
bootc saves its diagnostic in `/boot/bootc-finalize-failure.stamp`. When `/boot`
is not mounted, the persistent location is
`/sysroot/boot/bootc-finalize-failure.stamp`, not the image's read-only `/boot`.
Stored diagnostics and reads are bounded to 16 KiB. Successful finalization
removes a stale pending stamp, including when there is no staged deployment.

On the next composefs boot, `bootc-boot-complete.service` reports the saved
diagnostic and fails. It renames the stamp to
`bootc-finalize-failure.stamp.previous` in the same directory before reporting
it, retaining the diagnostic for inspection but consuming the pending failure
once. Subsequent boots do not fail this check unless another failure is
recorded. Successful finalization clears the pending stamp, not the retained
`.previous` diagnostic. Failure to persist or consume the stamp can prevent
this one-shot behavior.

The service runs only when `boot-complete.target` is requested and a pending
stamp exists. The bootc generator makes the service a required dependency of
that target on composefs systems, and the service is ordered before the target.
Both the requirement and the ordering are needed: a failed assessment then
prevents the target from being reached in that transaction, so consumers such
as `systemd-bless-boot.service` cannot bless that boot. The target is passive;
bootc does not pull it into the boot transaction. An image or administrator
must arrange for a boot assessment consumer to request it (for example,
enable `systemd-bless-boot.service` where supported). Without activation, the
stamp remains pending rather than being reported by this service.

Inspect the assessment and the previous shutdown with:

```bash
systemctl status bootc-boot-complete.service
journalctl -b -u bootc-boot-complete.service
journalctl -b -1 -u bootc-finalize-staged.service
```

This reports returned shutdown finalization errors, not every interrupted
shutdown or early-boot failure. For example, `bootc-root-setup.service` mounts
the composefs image and sets up `/etc` and `/var` during initramfs; if it fails,
the system may enter emergency mode or hang before assessment can run.
Android A/B finalization does not use this `/boot` stamp mechanism.

### Systemd Boot Assessment Integration

As of a recent OSTree with [this commit](https://github.com/ostreedev/ostree/commit/08487091256b93493f8d692e37ab3d892c758da1)
it is possible to configure the boot loader entry counting.

Failure reporting is separate from boot entry counting: the composefs backend
does not currently configure counting or automatic rollback. The opt-in
systemd-boot counting work in
[#25](https://github.com/cgwalters-forge/bootc/pull/25) is not part of this
branch. Its `/etc/kernel/tries` setting must not be assumed to enable counting
here. Combined blessing/fallback validation with that work remains a separate
integration gate. Failure reporting alone does not change GRUB or Android A/B
counting, rollback, or soft-reboot policy.
